# Lessons Learned

Reusable lessons about harness workflow, validation, orchestration, and engineering process -- grounded in a specific run and its retained evidence, not task-specific product trivia, and not a speculative recommendation presented as established fact. At most 5 new entries are appended per terminal run (see harness/orchestrator/memory.py's append_lessons and .claude/skills/work/SKILL.md's terminal memory-append step).

Format: `- [LESSON-ID] (source_run: <run_id>, evidence: <repo-relative path>, date: <YYYY-MM-DD>[, tags: <comma,separated,tags>]) <lesson text>`

- [L-20260806-TRANSPORT-BUDGET] (source_run: run-20260803-riskband-001, evidence: runs/run-20260803-riskband-001/logs/policy-events.jsonl, date: 2026-08-06, tags: transport,validation,json,correction-budget) Strict JSON transport failures (a fenced or prose-wrapped raw agent reply) must be classified and repaired separately from content failures, before any semantic or schema validation is attempted, and are only ever granted a single bounded correction attempt per phase rather than an unbounded retry loop.
- [L-20260916-ORCH-COMMAND-GRAMMAR] (source_run: run-20260916-hardfailbound-001, evidence: runs/run-20260916-hardfailbound-001/logs/ORCH-2.rejected.json, date: 2026-09-16, tags: test-runner,command-grammar,orchestrator,verification) The orchestrator's own ad hoc ORCH-* test-runner health-check commands are bound by the exact same strict positional command grammar as agent-requested commands (e.g. a bare 'python -m pytest -q' with no positional target is command_rejected, not silently accepted). Unlike an agent's rejected command -- which halts the phase -- a rejection of the orchestrator's own authored command is the orchestrator's own authoring mistake: retain the rejection as evidence, then correct the command and reissue it under a fresh command_id rather than escalating or blocking the run.
- [L-20260916-BRIDGE-NOT-APPLICABLE] (source_run: run-20260916-hardfailbound-001, evidence: runs/run-20260916-hardfailbound-001/obsidian/read/architect-mcp-1.json, date: 2026-09-16, tags: evidence-retention,verification,obsidian,least-privilege) An evidence-retention bridge that independently re-verifies an agent's self-reported affirmative observation (e.g. retain_architect_obsidian_reads re-reading an Architect's claimed mcp__obsidian__read_note) should classify a non-affirmative self-reported status (connector_unavailable, not_found, etc.) as a distinct 'not_applicable' outcome rather than attempting any independent re-check for it -- there is nothing affirmative to corroborate, and attempting one anyway would risk manufacturing evidence the original observation never made.
- [L-20260917-DISPATCH-RELATIVE-WORKDIR] (source_run: run-20260917-logicrepair-001, evidence: runs/run-20260917-logicrepair-001/logs/unknown.rejected.json, date: 2026-09-17, tags: test-runner,engineer,command-grammar,dispatch-prompt) When dispatching a live Engineer or Quality Engineer for a task that will request test-runner commands, state explicitly in the dispatch prompt that working_directory must be a relative path (e.g. 'demo-repo'), matching this repo's established convention -- engineer.md's own 'Command grammar' section documents the command string's grammar in detail but is silent on working_directory's relative/absolute requirement, so a live agent may reasonably supply an absolute path, producing an avoidable command_rejected that halts the phase outright (per the command_rejected escalation rule) rather than being repaired by the orchestrator.
- [L-20260918-CHECKPOINT-UNDERSTATES-PROGRESS] (source_run: run-20260917-logicrepair-002, evidence: runs/run-20260917-logicrepair-002/logs/policy-events.jsonl, date: 2026-09-18, tags: resume,checkpoint,evidence-audit) A checkpoint.json's own next_resume_action (e.g. 'dispatch the verification phase') can understate real prior progress: checkpoints are only written at fixed progress-boundary points (after a phase's canonical artifact promotes), never after every staged turn or mid-route-back-cycle. Before resuming a run, inspect the full retained evidence directory (attempts/, logs/, requests/, policy-events.jsonl) rather than trusting the checkpoint's own narrative of what has already been attempted -- run-20260917-logicrepair-002's checkpoint said Verification was untouched, but real retained evidence showed a full first-pass Verification (fail), a genuine route-back, and a partially-completed Engineer repair had already happened before the process that wrote that checkpoint was interrupted.
- [L-20260918-REPAIR-CYCLE-NOT-RESUMABLE-ACROSS-PROCESS] (source_run: run-20260917-logicrepair-002, evidence: runs/run-20260917-logicrepair-002/logs/policy-events.jsonl, date: 2026-09-18, tags: route-back,continuity,resume,repair-cycle) A same-run logic-repair route-back cycle is same-process by construction (work/SKILL.md: 'never itself resumed across a process restart'). If the process that started a repair cycle (post-verification-fail route-back to the Engineer) is interrupted before the Engineer's repair-round report is retained/validated/promoted, that cycle cannot be closed by any later resumed process: the orphaned Engineer agent identity is not resumable, and Implementation cannot be redispatched once it is already in a checkpoint's completed_phases. The correct, honest classification is a genuine continuity_broken terminal failure for that repair cycle -- never a fresh Engineer redispatch disguised as a continuation, and never silently treating the underlying source's already-fixed state as equivalent to a closed evidence chain, even when independent re-testing shows the code and full test suite are genuinely green.
- [L-20260918-FRESH-DISPATCH-COMMAND-ID-COLLISION] (source_run: run-20260917-logicrepair-002, evidence: runs/run-20260917-logicrepair-002/logs/policy-events.jsonl, date: 2026-09-18, tags: resume,command-grammar,test-runner,evidence-retention) When a checkpoint-resumed run dispatches a fresh subagent instance for a phase that a prior, interrupted process already made real (but uncheckpointed) progress on, the fresh agent's own command_id numbering restarts from its own examples (e.g. 'V-1') and can collide with that prior process's already-retained request/log evidence for the same command_id. The test-runner wrapper requires the request filename to exactly equal the command_id (no collision-avoidance suffix trick works), so the orchestrator must explicitly instruct the fresh agent to continue the run's real command_id sequence (e.g. start at 'V-3' when 'V-1'/'V-2' are already retained) rather than reusing its own default numbering, in order to avoid overwriting existing evidence.
- [L-20260918-HANDBACK-ENFORCE-PHANTOM-MESSAGES] (source_run: run-20260918-logicrepair-003, evidence: runs/run-20260918-logicrepair-003/logs/policy-events.jsonl, date: 2026-09-18, tags: continuity,dispatch,verification,tooling) When dispatching a staged subagent (Engineer/Quality Engineer) via the Agent/SendMessage tooling, a background '[handback-send-enforce]' mechanism can inject forced-handback messages into the agent's own turn sequence before the orchestrator's real reply arrives, causing the agent to correctly self-block per its own bounded-rejection rule even though neither the orchestrator nor the agent violated the documented protocol. Treat a resulting self-blocked report with zero real command evidence as a continuity_broken event (not a product/verification verdict), retain it honestly, and dispatch a genuinely fresh agent instance for that phase rather than trying to resume or promote the phantom-caused blocked report as canonical.
- [L-20260918-CHECK-CORE-BEFORE-DESIGNING-LIVE-CLI-FEATURE] (source_run: run-20260918-logicrepair-003, evidence: runs/run-20260918-logicrepair-003/verification-report.repair-1.json, date: 2026-09-18, tags: architecture,live_cli,core,reuse) Before designing a new mechanism for live_cli.py (the live orchestrator bridge), check whether harness/orchestrator/core.py's deterministic engine already solved the same problem -- it often has, since core.py is deterministically tested first and its own internal helpers (e.g. _validate_and_promote's filename override, driving the repair-round f'{stem}.repair-{n}.json' convention) can usually be extracted into a shared evidence_io.py function and reused by both, rather than inventing a parallel design. This closed the run-20260917-logicrepair-002 gap (FACT-20260918-PROMOTE-NO-REPAIR-PATH) cleanly: core.py already had the exact convention, live_cli.py just needed to expose it.
- [L-20260921-RECONSTRUCT-BEFORE-RERUN] (source_run: run-20260919-flaky-001, evidence: runs/run-20260919-flaky-001/checkpoint.json, date: 2026-09-21, tags: resume,checkpoint,evidence-audit,verification) When the process running a checkpoint-tracked pipeline is interrupted after checkpoint.json already reached status: complete with next_resume_action: null, reconstruct the terminal state from the run's full retained evidence directory (attempts, logs, verification-report.json, policy-events.jsonl, and any one-shot sentinel/state file) before taking any action. If that evidence independently corroborates every classification, retry, and route-back decision the checkpoint claims, finish only the missing terminal artifacts (run-summary.json, memory append, Obsidian publish) rather than re-dispatching a subagent, re-running verification, or re-triggering an already-consumed one-shot infrastructure-flake mechanism merely because run-summary.json is absent -- a missing terminal artifact is not evidence that the underlying work did not happen.
- [L-20260921-STALL-RESUME-SAME-AGENT] (source_run: run-20260919-flaky-001, evidence: runs/run-20260919-flaky-001/logs/policy-events.jsonl, date: 2026-09-21, tags: dispatch,continuity,engineer,tooling) A dispatched subagent that reports a stream-watchdog stall ('no progress for 600s') after being resumed mid-turn is a session/tooling anomaly, not necessarily a broken agent identity. Sending one further message to the exact same agent_id (rather than redispatching a fresh Engineer/Quality Engineer) can genuinely recover that identity and produce a correctly-continued, evidence-consistent turn referencing the same prior changed_files and command evidence. This differs from the cross-process interruption case (L-20260918-REPAIR-CYCLE-NOT-RESUMABLE-ACROSS-PROCESS), where the same agent identity truly cannot be resumed once the process itself restarts -- a same-process stall recovery and a cross-process continuity break are distinct failure modes requiring different responses.
- [L-20260929-EXPLICIT-CONTRACT-REMINDER-PER-TURN] (source_run: run-20260929-costproof-001, evidence: runs/run-20260929-costproof-001/logs/policy-events.jsonl, date: 2026-09-29, tags: transport,validation,dispatch-prompt,correction-budget) Appending the exact output-contract sentence (raw JSON only, no fence, no prose, first/last char {/}) to the end of every single Agent dispatch prompt and every SendMessage reply -- not just the initial dispatch -- correlates with a staged Engineer/Quality-Engineer/Architect protocol completing with zero transport_parse_failure events across an entire four-phase run (run-20260929-costproof-001), in contrast to the immediately preceding attempt at the same underlying fix (run-20260929-percentage-001), which hit two independent transport-contract violations from the same Engineer identity across two different staged turns without that per-turn reminder. This does not prove causation from a single before/after pair, but it is cheap, harmless, and directly targets the exact failure mode L-20260929-TRANSPORT-BUDGET-PER-PHASE-NOT-PER-TURN documents -- worth doing by default on every staged dispatch/resume, not only when a transport failure has already occurred once in the run.
